# Community moderation workspace

The existing `/admin/message-reports` route is now Community moderation, with Reports (including an Appeals queue), Flagged content and Conversation review. Support remains in the separate admin Inbox. Ordinary member reads and downloads still require direct-conversation membership. Authorized moderators now have a separate, explicit reason-based review path. This replaces the former selected-message-only review policy.

## Access, review reasons and evidence

The existing SUPER_ADMIN role editor delegates `direct-reports:review`, `community:conversations`, `community:attachments` and `community:actions`. Built-in ordinary staff receive no new grants. Attachment/action permissions depend on conversation review. Existing SUPER_ADMIN controls, session revocation and role-revision checks remain in place.

Conversation metadata lookup is audited. Opening history requires a reason of 10–1,000 characters and creates a 15-minute grant bound to the reviewer, admin session and conversation. Every history page and permitted/denied scanner-gated file request is audited. Grants cannot be reused by another reviewer, another admin session or after expiry. Every request rechecks current permissions. The audit API has no update/delete route; audit records are append-only through the application. They are not advertised as tamper-proof against database administrators.

New reports retain the conversation reference and selected-message evidence. Legacy selected-message reports resolve their conversation from the original message IDs; linked enforcement verifies those IDs before associating the case. Messages and file bytes are retained. Case history records investigations, dismissals and reversals. Quarantine prevents future server downloads; it cannot recall copies downloaded earlier.

Warnings, messaging restrictions and community suspensions require reasons. Only members in the reviewed conversation can be targeted; staff accounts cannot be suspended through this workspace. Community suspension prevents community writes, friend requests/acceptance and new direct messages, while keeping sign-in, history, direct Block/Report, Safety notices, appeals and Contact support available. It does not disable the underlying account or unrelated Academy access. Unfriend/cancel/decline remain available. Each enforcement is independently reversible; reversing one restriction does not remove another active restriction. Reversing a quarantine cannot bypass scanning.

The existing notification bell delivers issued/reversed actions and appeal outcomes, including attachment-quarantine notices to the uploader. `/blog/safety` shows only the signed-in member's notices and appeal history, with Contact support. Appeals are owner-scoped and deduplicated. Authorized reviewers open the associated conversation with a reason, reverse an action if appropriate, and resolve the appeal with a recorded response. No external email/SMS is added.

## File safety and scanner operation

Private direct and support attachments retain the existing 3-file/message, 8 MiB/file and per-account limits, image decoding/re-encoding, PDF signature checks and audio-container checks. Executables, script/HTML/SVG extensions, executable/archive signatures and unsupported archives are rejected. Obvious active PDF features are rejected; PDFs are downloaded, not embedded as active documents. This is not a claim that every possible active or malicious document is detected.

The ClamAV client implements the official [clamd INSTREAM protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html). Both original bytes and transformed image bytes must receive clean verdicts. Only an exact successful scanner verdict is accepted. Missing configuration yields `pending`; connection, protocol, timeout and busy failures yield `scan_failed`; a detection yields `infected`. All are quarantined. Old files without scan state are unscanned, never implicitly safe. With a configured scanner, the durable worker scans older/pending/failed files before release. Infected files require an explicitly audited moderation rescan; manual quarantine is separate and remains in force until reversed.

Configure a trusted private clamd service using `MALWARE_SCANNER_HOST` and `MALWARE_SCANNER_PORT` (default 3310), with current signature databases and `StreamMaxLength` covering the upload limit. Do not expose unauthenticated clamd to the public Internet. The application caps concurrent scan requests and times out unavailable scans. The optional local Compose override now provisions a working scanner and enables the embedded MongoDB scan worker; see [startup and retry instructions](attachment-scanning.md). Unscanned files remain unavailable until a successful verdict. No production deployment was performed.

Downloads enforce membership or the dedicated attachment-review permission and review grant, scanner state and manual quarantine. Responses use private/no-store caching, nosniff, same-origin resource policy, CSP sandbox, sanitized names and PDF attachment disposition. Images/audio are served through protected endpoints; text is rendered as text. Successful scanning is not a guarantee of absolute safety.

## Review signals and tests

Message/upload rate limits and blocking remain server-side. `COMMUNITY_FLAG_TERMS` is a JSON array of up to 50 literal strings, each 1–256 characters; `COMMUNITY_MAX_LINKS` defaults to 8 (1–50). Repeated messages and attachment scan failures/pending verdicts also create deduplicated review flags. These are signals, not conclusions that content is illegal. No private content is sent to external AI services, and complete detection is not promised.

`backend/test/community-moderation.integration.test.mjs` uses isolated MongoDB data, actual authenticated member/admin sessions and a local clamd protocol simulator. It tests delegated permissions, review reasons/session binding/expiry, file audit, missing/failed/infected/clean verdict policy, quarantine, reversal, appeals, notifications, flags, pagination and preservation. The simulator tests application policy and protocol handling, not real malware detection. Existing messaging/friendship/media tests use this same explicitly isolated scanner fixture. `frontend/test/community-moderation-browser.mjs` exercises the rendered workspace and member appeal page against isolated real APIs, including permission-protected previews, quarantine/reversal, restrictions, appeals, refresh persistence and desktop/mobile overflow checks. Screenshots are saved in `artifacts/community`. The local ClamAV clean/EICAR checks and durable scan queue tests are documented in [attachment scanning](attachment-scanning.md).
